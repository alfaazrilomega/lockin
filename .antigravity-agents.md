### 🔴 MISTAKE #1 — "Copy the animation" ≠ "Copy everything"

**What happened (Session: contact page, April 2026):**
User asked: _"copy animation hover on our button 'OUR APPROACH' and paste it to 'HIT ME UP!'"_
Agent incorrectly copied the **full component** (`FlowHoverButton`) — including its arrow icon, pill shape, and border — changing the entire visual identity of the target button. User only wanted the **hover animation behavior** transferred.

**Root cause:** Assumed "copy" = clone entire component. Did not verify scope.

**Prevention — SCOPE CLARIFICATION PROTOCOL (MANDATORY):**

> When the user says **"copy X from A to B"**, **"same as"**, **"like"**, **"use the one from"**, or **"apply that to"**:
>
> 1. Read the **source component** first.
> 2. Identify ALL things it contains (shape, color, icon, animation, spacing, font).
> 3. **ASK before executing** if ANY ambiguity exists between "copy the behavior" vs "copy the whole thing".
>
> **Clarification format:** _"Just to confirm — you want only the [hover animation], keeping the button's existing [shape/color/content]? Or replicate the full style too?"_
>
> **Default assumption:** "copy the animation" = **only the animation logic**. Preserve ALL other visual properties of the target unless explicitly told otherwise.
>
> **Absolute Rule:** NEVER add an icon, change shape, or alter visual identity when user only asked for an interaction/animation behavior.

### 🔴 MISTAKE #2 — Tailwind `group-hover` fires on parent section, not button

**What happened (Session: contact page, April 2026):**
`StaggeredHoverText` used `group-hover:-translate-y-full`. The button had `class="group"`. But the parent `<section>` **also had `group`** for opacity transitions. Tailwind resolves `group-hover` to the **nearest ancestor with `group`** — so the animation fired whenever the user hovered anywhere in the section, not just on the button.

**Root cause:** Did not audit parent tree for existing `group` usage before using `group-hover` in a child.

**Prevention — TAILWIND NAMED GROUP PROTOCOL (MANDATORY):**

> Before using `group` + `group-hover` on ANY element:
>
> 1. Grep or read the parent chain for existing `group` class usage: `grep "className.*\bgroup\b"`.
> 2. If a parent already has `group`, **ALWAYS** use Tailwind's **named group syntax**:
>    - Target: `group/btn`
>    - Children: `group-hover/btn:-translate-y-full`
> 3. This rule applies to ALL Tailwind variant modifiers: `group`, `group-focus`, `group-active`, `peer`, `peer-hover`, etc.
>
> **Absolute Rule:** NEVER use bare `group-hover` inside a component that lives inside a section/layout that already uses `group`. Named groups are mandatory in those situations.

### 🔴 MISTAKE #3 — Local "npm run build" Success ≠ Vercel Lambda Success (Next.js App Router)

**What happened (Session: Vercel Auth Deployments, April 2026):**
The local `npm run build` command succeeded entirely (`Exit code: 0`). However, the Vercel deployment constantly failed with the fatal error `Error: Unable to find lambda for route: /auth/forgot-password`. The agent assumed local build success guaranteed Vercel success, leading to frustrating redeployment loops instead of fixing the code.

**Root cause:**
Vercel's specific Serverless/Edge lambda bundler crashes when it attempts to package Server Components that rely on dynamic context (like Supabase Auth which reads `cookies()` deep within its client tree) without an explicit route segment config. Local `next build` gracefully falls back, but Vercel's cloud infrastructure throws a fatal lambda linking error.

**Prevention — VERCEL DYNAMIC ROUTE PROTOCOL (MANDATORY):**

> 1. **Local CLI does NOT equal Vercel Cloud:** Never assume `npm run build` proves a flawless Vercel deployment. If Vercel fails on the server, you must run `npx vercel build` locally to replicate the exact lambda-packing step.
> 2. **Enforce `force-dynamic`:** If you are building or editing an API Route (`/api/.../route.ts`) OR a Page (`page.tsx`) that reads Authentication state, cookies, headers, or bypasses static generation:
>    - You **MUST** include `export const dynamic = "force-dynamic";` at the top of the file.
> 3. **Dynamic Defaults:** Always assume pages interacting with `@supabase/auth-helpers-nextjs` or `@supabase/ssr` must be forcefully set as dynamic to prevent `Unable to find lambda` errors.
